RAGspace

RAGspace is a full-stack conversational Retrieval-Augmented Generation (RAG) platform that allows users to create isolated knowledge spaces, upload documents, and have AI-powered conversations grounded in those documents.

Rather than relying primarily on an LLM's pretrained knowledge, RAGspace retrieves relevant information from a user's private document collection and provides that information to an LLM as context for generating grounded answers with source references.

RAGspace is designed as both a practical AI application and a demonstration of production-oriented full-stack, cloud, retrieval, and machine-learning architecture.

File Storage — AWS S3

Original uploaded PDFs are stored in AWS S3.

S3 is used for durable object storage rather than storing large binary files directly in MySQL or on the EC2 filesystem.

A conceptual object structure is:

ragspace/
    users/
        <user-id>/
            documents/
                <document>

The original document is retained even after RAG ingestion completes.

Keeping the original provides several advantages:

Users can access the source document later.
Source citations can link back to the original.
Documents can be reprocessed.
Documents can be re-chunked.
Documents can be re-embedded if the embedding model changes.
Future extraction improvements can operate against the original source.

Chunks themselves are not stored in S3.

Vector Database — Qdrant Cloud

RAGspace uses Qdrant Cloud as its dedicated vector database.

The planned collection is:

Upload Restrictions

V1 intentionally limits document ingestion to keep resource usage predictable.

Initial limits:

File type:              PDF
Maximum file size:      10 MB
Maximum documents/user: 20
Maximum pages:          approximately 200

An extracted-text or token limit should also be enforced.

File size alone does not accurately represent embedding workload because two PDFs of identical size can contain dramatically different amounts of extractable text.

Both frontend and backend validation should exist.

Backend validation remains authoritative because frontend validation can be bypassed.

Encrypted/password-protected PDFs and documents without usable extractable text should fail gracefully.

OCR for scanned documents is not part of V1.

Chunking

Extracted text is divided into overlapping chunks before embedding.

Initial values will be configurable rather than permanently hard-coded.

A reasonable starting configuration is approximately:

Chunk size:    500-800 tokens
Chunk overlap: 100-150 tokens

Overlap helps preserve semantic context when paragraphs, explanations, or sections cross chunk boundaries.

Too much overlap is intentionally avoided because it creates redundant embeddings, increases storage, and can return repetitive retrieval results.

Structure-aware chunking may be introduced in a future version.

This architecture separates retrieval from generation.

The LLM does not consume embedding vectors.

Embedding vectors are used by Qdrant to identify relevant chunks.

The actual text contained in those retrieved chunks is then supplied to the LLM.

Conversational Query Contextualization

RAGspace supports conversational follow-up questions.

A question such as:

"Can you explain the second part?"

contains insufficient semantic information for high-quality vector retrieval by itself.

RAGspace therefore uses recent conversation history to transform context-dependent questions into standalone retrieval queries.

Conceptually:

Previous conversation
        +
Current question
        |
        v
GPT
        |
        v
Standalone retrieval query
        |
        v
Embedding
        |
        v
Qdrant

The rewritten query is used for retrieval.

The user's original question remains the question used during final answer generation.

Conversation Memory

Conversation history is stored in MySQL.

RAGspace does not send unlimited conversation history to the LLM.

V1 uses a configurable recent-message window, initially around:

8 messages

This gives the model enough context for conversational continuity without continuously increasing prompt size and inference cost.

Long-term conversation summarization is reserved for V2.

Similarity Search

The contextualized query is embedded using the same embedding model used during document ingestion.

Qdrant then performs vector similarity search against eligible document chunks.

Retrieval is filtered by the authenticated user and active Space.

Conceptually:

Question Vector

        vs.

Stored Chunk Vectors

        |

Semantic Similarity

        |

Top Candidate Chunks

The initial candidate count is expected to be approximately:

12

This value remains configurable.

Relevance Threshold

RAGspace does not automatically trust every nearest-neighbor result.

A configurable minimum relevance threshold is applied.

Without a threshold, a vector database can return the mathematically closest chunks even when none of them actually contain relevant information.

If no retrieved chunks meet the required relevance level, RAGspace should respond that sufficient information could not be found in the selected Space rather than allowing the LLM to generate an unsupported answer from general knowledge.

Reranking

RAGspace supports optional second-stage reranking.

The planned reranker is:

Voyage rerank-2.5-lite

The retrieval strategy becomes:

Qdrant
   |
Top ~12 Candidates
   |
Similarity Threshold
   |
Voyage Reranker
   |
Best ~5 Chunks
   |
LLM

Reranking is intentionally optional.

If the reranking service is unavailable, the core RAG pipeline must continue functioning.

Reranker Available:

Qdrant -> Threshold -> Rerank -> Generation


Reranker Unavailable:

Qdrant -> Threshold ---------> Generation

This provides graceful degradation and prevents an enhancement service from becoming a single point of failure.

Generation

The initially selected generation model is:

GPT-5 mini

The specific model should be controlled through configuration/environment variables rather than being hard-coded throughout the application.

The generation request receives:

System instructions
Recent conversation context
Original user question
Retrieved chunk text
Source metadata

The model should be explicitly instructed to prioritize retrieved information and avoid presenting unsupported general knowledge as information from the user's documents.

If the retrieved context does not support an answer, the system should say so.

Design Philosophy

RAGspace follows several core engineering principles:

Separation of concerns

MySQL, S3, Qdrant, Django, React, and AI services each have clearly defined responsibilities.

Cloud-first AI inference

Embedding, vector retrieval, reranking, and generation workloads are kept off the resource-constrained application server where practical.

Retrieval before generation

The LLM is not treated as the application's knowledge database. Relevant information is retrieved first and then supplied as grounded context.

Source traceability

Answers should expose where retrieved information originated.

Graceful degradation

Optional components such as reranking should improve retrieval without becoming mandatory for the core application to function.

Configurable retrieval

Chunk sizes, overlap, thresholds, candidate counts, history windows, reranking, and model choices should be adjustable.

Secure multi-user isolation

Every retrieval and data operation must respect authenticated ownership boundaries.

Build for today without blocking tomorrow

V1 avoids premature distributed-system complexity while preserving clear migration paths toward asynchronous processing, horizontal scaling, and commercial SaaS infrastructure.
